# B 2단계 입문자용 이해와 검증 가이드

이 문서는 ReproLoop와 같은 기술 구성으로 처음 개발하는 사람도 2단계 결과를 이해하고 직접 정상 여부를 판단할 수 있도록 작성했다.

코드를 모두 이해할 필요는 없다. 먼저 자동 검사를 통과시키고, 그다음 실제 DB에서 핵심 동작 세 가지를 확인하면 된다.

## 문서 사용법

목적에 따라 아래 순서로 읽으면 된다.

| 목적 | 읽을 부분 |
|---|---|
| 기술을 먼저 이해하고 싶음 | 1장 → 2장 → 3장 |
| 바로 테스트하고 싶음 | 4장 → 5장 → 6장 → 7장 |
| migration을 확인하고 싶음 | 8장 |
| 최종 합격 여부만 판단하고 싶음 | 9장 → 11장 |
| 오류를 팀원에게 전달해야 함 | 10장 |

가장 중요한 안전 규칙은 **운영 DB로 통합 테스트나 migration을 실행하지 않는 것**이다.

## 1. 이번 단계에서 무엇을 만든 것인가

ReproLoop에서 Discord 사용자가 버그를 제보하면 다음과 같은 일이 필요하다.

```text
Discord에서 버그 제출
        ↓
입력값과 프로젝트·빌드 확인
        ↓
DB에 버그 제보 저장
        ↓
"제보가 생성됨" 이력 저장
        ↓
웹 화면과 알림 기능이 같은 데이터를 사용
```

2단계에서는 이 흐름의 **DB와 업무 규칙 기반**을 만들었다. Discord 화면이나 웹 화면 자체를 만든 단계는 아니다. 따라서 아직 `/bug` 명령을 Discord에서 실행해 볼 수 없는 것이 정상이다. 그 연결은 3단계 작업이다.

이번 단계에서 만든 핵심 결과는 다음과 같다.

| 결과 | 쉬운 설명 |
|---|---|
| DB schema | 어떤 종류의 데이터를 어떤 모양으로 저장할지 정한 설계도 |
| migration | 이미 존재하는 DB를 새 설계도에 맞게 변경하는 작업 지시서 |
| DB factory | 앱이 필요한 DB 주소로 안전하게 연결하고 연결을 닫는 도구 |
| repository | 업무 코드가 SQL 세부사항을 몰라도 제보를 읽고 수정하게 해주는 창구 |
| 제보 생성 command | 제보 한 건을 안전하게 저장하는 전체 절차 |
| 자동 테스트 | 위 규칙이 깨지지 않았는지 반복 확인하는 검사 |

## 2. 사용한 기술을 쉽게 이해하기

### 2-1. PostgreSQL과 Supabase

- **PostgreSQL**은 데이터를 실제로 저장하는 데이터베이스다.
- **Supabase**는 PostgreSQL을 쉽게 운영할 수 있게 관리 화면, 인증, Storage 등을 함께 제공하는 서비스다.
- 이 프로젝트의 `.env`에 있는 `DATABASE_URL`은 앱이 PostgreSQL에 접속하기 위한 주소다.

비유하면 PostgreSQL은 창고이고, Supabase는 창고를 관리하는 서비스이며, `DATABASE_URL`은 창고 열쇠가 포함된 주소다. 따라서 이 값은 Git에 올리거나 화면에 공개하면 안 된다.

### 2-2. Drizzle ORM

DB는 보통 SQL로 다룬다. Drizzle은 TypeScript 코드로 테이블과 조회를 표현하고, 잘못된 필드 이름이나 타입을 개발 중에 발견하도록 돕는다.

- `packages/db/src/schema/`: 테이블 설계
- `packages/db/src/repositories/`: 실제 DB 조회·수정 코드
- `packages/db/drizzle/`: DB 구조 변경 이력

Drizzle을 사용한다고 SQL이 없어지는 것은 아니다. TypeScript 코드와 PostgreSQL 사이를 안전하게 연결해주는 역할이라고 이해하면 된다.

### 2-3. schema와 migration의 차이

둘은 비슷해 보이지만 역할이 다르다.

| 구분 | 의미 | 비유 |
|---|---|---|
| schema | 현재 코드가 기대하는 최종 DB 구조 | 건물의 최신 설계도 |
| migration | 이전 DB를 다음 구조로 바꾸는 순서 | 실제 증축 공사 지시서 |

schema 파일만 수정하면 이미 만들어진 Supabase DB는 바뀌지 않는다. migration을 적용해야 실제 DB가 바뀐다.

이번 작업은 기존 `0000`을 지우지 않고 `0001_full_schema_alignment.sql`을 추가했다. 기존 기록을 보존하면서 다음 변경을 쌓는 방식이다.

### 2-4. Shared, Domain, DB package

프로젝트가 역할별 package로 나뉜 이유는 서로 다른 책임을 섞지 않기 위해서다.

```text
@reproloop/shared
  여러 앱이 함께 쓰는 값과 입출력 형태
          ↓
@reproloop/domain
  제보 상태 변경 같은 업무 규칙
          ↓
@reproloop/db
  위 규칙을 PostgreSQL에 실제로 저장
```

예를 들어 `investigating`이라는 상태가 Shared와 DB에서 다르게 적혀 있으면 앱은 정상 동작하지 않는다. schema 테스트가 두 값의 완전 일치를 검사한다.

### 2-5. transaction과 rollback

제보를 만들 때는 다음 두 기록이 함께 저장되어야 한다.

1. `bug_reports`에 제보 본문 저장
2. `status_events`에 `report_created` 이력 저장

첫 번째만 성공하고 두 번째가 실패하면 데이터가 불완전해진다. **transaction**은 이 작업들을 하나로 묶는다. 중간에 하나라도 실패하면 **rollback**되어 전부 이전 상태로 돌아간다.

은행 송금에서 한쪽 계좌의 돈만 빠지고 다른 쪽 계좌에는 들어가지 않는 상황을 막는 것과 비슷하다.

### 2-6. 멱등성과 unique 제약

Discord나 네트워크는 같은 요청을 재전송할 수 있다. 같은 제보가 두 번 저장되면 안 되므로 Discord interaction ID를 한 번만 저장할 수 있게 만들었다.

- 첫 요청: 새 제보 생성, `created: true`
- 같은 요청의 재시도: 기존 제보 반환, `created: false`
- DB unique 제약: 동시에 요청이 들어와도 최종 중복을 차단

이런 식으로 같은 요청을 여러 번 실행해도 최종 결과가 한 번 실행한 것과 같게 만드는 성질을 **멱등성**이라고 한다.

### 2-7. 낙관적 잠금과 version

두 관리자가 같은 제보를 동시에 수정하면 늦게 저장한 사람이 앞선 변경을 덮어쓸 수 있다. 이를 막기 위해 제보마다 `version` 숫자를 둔다.

```text
관리자 A와 B가 version 0을 읽음
A가 먼저 저장 → version 1
B가 version 0으로 저장 시도 → CONFLICT로 거절
```

이 방식이 **낙관적 잠금**이다. 충돌을 조용히 덮어쓰지 않고 사용자에게 다시 불러오도록 알릴 수 있다.

### 2-8. enum, 제약, 인덱스

- **enum**: 허용할 값을 제한한다. 예: 제보 상태는 정해진 6개만 허용한다.
- **제약(constraint)**: 잘못된 데이터가 저장되지 못하게 한다.
- **unique 인덱스**: 중복을 금지한다.
- **일반 인덱스**: 자주 찾는 데이터를 빠르게 조회하게 한다.
- **외래 키(FK)**: 존재하지 않는 프로젝트나 빌드를 가리키지 못하게 한다.

애플리케이션 코드의 검증은 실수로 빠질 수 있다. DB 제약은 저장 직전의 마지막 방어선이다.

## 6. 실제 PostgreSQL 통합 테스트

이 검사는 DB에 임시 user, organization, guild, project, build, report를 만들었다가 종료 시 삭제한다. **운영 DB가 아닌 개발 DB인지 확인한 후** 실행한다.

### 6-1. `.env` 값을 안전하게 테스트 변수로 전달

아래 명령은 URL을 콘솔에 출력하지 않는다.

```powershell
$databaseLine = Get-Content .env | Where-Object { $_ -match '^\s*DATABASE_URL\s*=' } | Select-Object -First 1

if (-not $databaseLine) {
  throw '.env에서 DATABASE_URL을 찾지 못했습니다.'
}

$env:TEST_DATABASE_URL = ($databaseLine -replace '^\s*DATABASE_URL\s*=\s*', '').Trim().Trim('"').Trim("'")
corepack pnpm --filter @reproloop/db test
Remove-Item Env:TEST_DATABASE_URL
```

성공 기준:

```text
Test Files  2 passed (2)
Tests       7 passed (7)
```

### 6-2. 이 테스트가 실제로 확인하는 것

| 테스트 | 일부러 만드는 상황 | 성공 판단 |
|---|---|---|
| 중복 interaction | 같은 제보 요청을 연속 두 번 실행 | report 1건, 생성 event 1건 |
| transaction rollback | 유효하지 않은 actor로 event 저장 실패 유도 | report 상태와 version이 원래대로 유지 |
| stale version | version 0으로 수정한 뒤 다시 version 0 수정 | 두 번째 수정은 `CONFLICT`, 첫 수정은 유지 |

통합 테스트 도중 실패하면 정리 코드가 일부 실행되지 못했을 가능성이 있다. `integration-`으로 시작하는 테스트 데이터를 Supabase에서 확인한 뒤 삭제 여부를 검토한다. 원인을 모르는 상태에서 다른 데이터를 일괄 삭제하지 않는다.

## 7. 실제 DB 구조를 눈으로 확인하는 방법

Supabase Dashboard의 **SQL Editor**에서 아래 쿼리를 각각 실행한다. 모두 조회 전용이다.

### 7-1. MVP 테이블 11개 확인

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name in (
    'users',
    'organizations',
    'organization_members',
    'discord_guilds',
    'game_projects',
    'builds',
    'bug_reports',
    'attachments',
    'status_events',
    'notifications',
    'product_events'
  )
order by table_name;
```

성공 기준: 결과가 정확히 **11행**이다.

### 7-2. 제보 상태 6개 확인

```sql
select enumlabel
from pg_enum
join pg_type on pg_type.oid = pg_enum.enumtypid
where pg_type.typname = 'report_status'
order by pg_enum.enumsortorder;
```

성공 기준:

```text
new
needs_info
investigating
reproduced
fixed
duplicate
```

### 7-3. 핵심 중복 방지 규칙 확인

```sql
select indexname
from pg_indexes
where schemaname = 'public'
  and indexname in (
    'bug_reports_project_number_uidx',
    'bug_reports_discord_interaction_id_uidx',
    'notifications_idempotency_key_uidx',
    'builds_project_version_uidx'
  )
order by indexname;
```

성공 기준: 결과가 **4행**이다. 이름 하나가 빠져 있으면 migration과 실제 DB 구조가 어긋난 것이다.

조직 멤버 중복은 별도 unique 인덱스가 아니라 두 열을 묶은 primary key로 막는다.

```sql
select constraint_name
from information_schema.table_constraints
where table_schema = 'public'
  and table_name = 'organization_members'
  and constraint_type = 'PRIMARY KEY';
```

성공 기준: `organization_members_organization_id_user_id_pk`가 한 행 나온다.

### 7-4. migration 적용 개수 확인

```sql
select count(*) as migration_count
from drizzle.__drizzle_migrations;
```

성공 기준: 현재 개발 DB에서는 `2`다.

> 다른 환경은 시작 시점이 다르면 숫자가 다를 수 있다. 단순히 숫자를 맞추기 위해 migration 테이블을 직접 수정하면 안 된다.

## 8. schema와 migration이 일치하는지 확인

`.env`의 `DATABASE_URL`이 개발 DB를 가리키는지 확인한 뒤 실행한다.

```powershell
corepack pnpm --filter @reproloop/db db:generate
```

성공 기준:

```text
No schema changes, nothing to migrate
```

새 migration 파일이 생성된다면 코드의 schema와 기록된 migration이 다르다는 뜻이다. 생성된 파일을 바로 적용하지 말고 차이를 먼저 검토한다.

### migration 적용 명령은 언제 쓰는가

```powershell
corepack pnpm --filter @reproloop/db db:migrate
```

이 명령은 실제 DB를 변경한다. 현재 개발 DB에는 이미 2단계 migration이 적용되어 있으므로 정상이라면 새 작업이 없어야 한다.

다음 경우에는 실행을 멈춘다.

- URL이 개발 DB인지 확신할 수 없음
- 운영 DB일 가능성이 있음
- 기존 bootstrap 테이블에 실제 데이터가 있음
- migration 안전장치가 오류를 발생시킴

안전장치 오류는 테스트 실패가 아니라 기존 데이터를 자동으로 지우지 않기 위한 의도된 중단이다.

- `db:generate`가 예상하지 않은 새 migration을 생성함

## 10. 문제가 생겼을 때 기록할 정보

팀원에게 도움을 요청할 때 비밀값을 제외하고 다음 정보를 전달한다.

```text
1. 실행한 명령

3. 오류 메시지 전체
4. 현재 브랜치 이름
5. git status --short 결과
6. Node와 pnpm 버전
7. 개발 DB인지 여부 — URL 자체는 전달하지 않음
```

DB 오류라면 Supabase의 테이블 전체 데이터를 공유하지 말고, 실패한 제약 또는 migration 이름만 먼저 전달한다.
