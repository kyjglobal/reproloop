# ReproLoop 최종 구현 계획

## 1. 프로젝트 완료 기준

외부 팀의 Discord 서버 관리자가 배포 패키지와 [README](../README.md)만 보고 자기 PC나 내부 서버에 ReproLoop를 설치한다. 관리자 웹에서 팀과 프로젝트·빌드를 등록하고, 제공된 Discord 봇을 서버에 추가해 설치본에 연결한다. 실제 테스터가 `/bug`로 제출한 제보가 고객의 PostgreSQL에 저장되고, 담당자가 대표 제보를 수정 완료 처리하면 관련 제보자가 수정 빌드 안내를 받는다.

ReproLoop 운영 범위는 공용 Discord 봇과 그 봇에 포함되는 로컬 연결 기능이다. 고객은 관리자 웹, PostgreSQL, 알림 큐와 Worker, 연결 프로세스 및 데이터 백업을 자기 환경에서 운영한다. 고객은 설치 화면에서 계정을 만들고 Discord에서 받은 연결 코드를 입력해 설정을 마친다.

## 2. 착수 시점과 구현 범위

| --- | --- | --- |

| 관리자 웹 | Discord OAuth 로그인, 조직·프로젝트 권한, 제보 목록·상세·상태 변경·병합이 있음. | 첫 관리자 계정과 팀을 만드는 초기 설정, 로컬 로그인, 서버 연결 상태, 프로젝트·빌드 생성 화면 구현. |

| 배포 | 소스 실행 스크립트와 테스트, 루트 CI가 있음. | 고객용 버전별 설치 패키지, 초기 설정, 서비스 상태와 오류 안내, 새 기기 설치 검증. |

## 3. 연결 설계

**제공 봇과 고객 설치본은 아웃바운드 HTTPS 롱폴링으로 연결한다.** 고객 설치본이 연결을 시작하고, 봇은 대기 중인 요청에 응답하는 형태로 `/bug` 작업을 전달한다. 별도 연결 서버 없이 기존 HTTP 엔드포인트를 운영하는 서비스에서 이 연결을 관리한다. 로컬 웹은 기본적으로 `127.0.0.1:3000`, PostgreSQL은 Compose 내부 네트워크에 둔다. [Discord 상호작용 수신·응답 문서](https://docs.discord.com/developers/interactions/receiving-and-responding#receiving-an-interaction)

- **연결 시작.** 제공 봇을 서버에 추가한 뒤 서버 관리 권한이 있는 사용자가 `/reproloop connect`를 실행한다. 봇은 해당 Discord 서버에 묶인 일회용 코드를 본인에게 표시한다. 로컬 `owner`가 설치 화면에 코드를 입력하면 로컬 설치 ID와 취소 가능한 자격 증명이 발급된다. 첫 릴리스의 구현 단위는 Discord 서버 한 곳당 로컬 설치본 한 개로 잡는다. 한 설치본에 여러 프로젝트와 빌드를 등록한다.
- **접수 처리.** 봇은 Discord 서명과 서버 ID를 확인한 뒤 연결된 설치본을 찾아 프로젝트·빌드 자동완성, 모달 표시, 모달 제출을 처리한다. 자동완성과 모달 열기는 첫 응답 시간인 3초 안에 처리하도록 연결 요청에 더 짧은 제한을 둔다. 모달 제출은 먼저 처리 중 응답을 보내고, 로컬 DB 커밋 결과가 돌아오면 `BUG-번호`를 보여준다. 상호작용 토큰은 봇 쪽에서 응답에만 사용한다. [Discord 응답 시간과 콜백 유형](https://docs.discord.com/developers/interactions/receiving-and-responding#responding-to-an-interaction)
- **알림 처리.** 수정 완료 시 로컬 DB에 저장된 알림을 Worker가 읽고, 설치본과 발송 대상의 자격을 확인한 봇이 DM을 보낸다. 고객 설치 패키지의 자격 증명은 해당 설치본에 한정한다. Discord Bot Token은 봇 운영 환경에 보관한다.
- **데이터 보관.** 팀·프로젝트·빌드·제보 본문·처리 이력·알림 기록은 고객 로컬에 저장한다. 봇 운영 환경에는 설치 ID, 서버 ID, 연결 자격 증명 해시와 연결 해제 상태 등 다시 연결하는 데 필요한 최소 정보만 유지한다. 제보 본문과 DM 정보는 Discord와 봇 간 처리 중 전달되며, 봇의 접수·발송 로그는 요청 ID와 처리 결과 중심으로 남긴다.
- **연결 끊김.** 설치본이 오프라인이면 폼을 열 수 없는 이유나 연결 상태를 Discord에 표시한다. 접수 요청 후 저장 결과가 불명확하면 결과 확인 실패를 안내한다. 로컬에 이미 저장된 제보와 대기 중인 알림은 로컬에 유지하고 연결이 돌아오면 발송 작업을 재개한다.

## 4. 구현 순서와 완료 조건

### 1단계 · 로컬 PostgreSQL과 초기 설정

- Compose로 Web·PostgreSQL·Worker를 묶고 로컬 데이터 볼륨을 둔다. 설치별 DB 비밀번호와 세션 비밀을 먼저 생성·보관하고, DB 기동을 확인한 뒤 기존 마이그레이션을 적용한다. 실패하면 초기 설정에 원인과 다음 조치를 표시한다.
- 초기 설정에서 `owner` 계정과 첫 팀을 한 번만 만들 수 있게 한다. 로컬 비밀번호 해시와 기존 세션·조직 역할 검사 흐름을 연결한다. 고객은 로컬 계정으로 로그인하고, `owner`는 팀원의 계정과 역할을 관리한다.
- 관리자 화면에서 첫 프로젝트, 문제 발생 빌드, 수정 빌드를 일상적으로 등록할 수 있게 한다. `owner/admin/member` 권한은 기존 도메인 규칙에 맞춰 유지한다.
- **완료 조건** — 빈 DB에서 설치를 시작해 SQL 수동 입력 없이 관리자 로그인과 첫 프로젝트·빌드 등록을 마친다. 컨테이너 재시작 후 같은 DB와 계정으로 접속한다.

### 2단계 · 제공 봇 초대와 `/bug` 연결

- 제공 봇의 초대 링크, 서버 설치 권한, 명령 등록 전략, 기존 상호작용 엔드포인트를 확인한다. 다른 테스트 서버에서 초대와 명령 표시를 먼저 검증한다. [Discord 서버 앱 설치 문서](https://docs.discord.com/developers/quick-start/getting-started#installing-your-app)
- 일회용 코드의 단일 사용·만료, 설치 토큰 발급·회전·폐기, 자동 재연결, 로컬 화면의 연결 상태 표시를 구현한다. 요청과 응답을 Discord 서버 ID와 설치 ID에 묶고, 연결 교체 시 이전 자격 증명의 권한을 폐기한다.
- 기존 `/bug` 검증과 접수 서비스를 로컬 DB에 연결한다. 봇은 필요한 필드만 로컬에 전달하고, 기존 상호작용 ID로 같은 제출 요청이 한 번만 저장되게 한다. 두 고객 설치본을 함께 띄워 요청과 응답이 올바른 설치본으로 가는지 확인한다.
- **완료 조건** — 서버 관리자와 로컬 `owner`가 연결을 완료한 후 실제 Discord 서버에서 `/bug`를 제출하면, 연결된 설치본에 제보와 접수 이력이 한 건씩 생기고 Discord에서 같은 `BUG-번호`가 보인다. 다른 서버의 프로젝트·빌드는 노출되지 않는다.

### 3단계 · 제공 봇으로 수정 알림 보내기

- 로컬 Worker의 직접 Discord 호출을 봇 발송 요청으로 바꾼다. 발송은 연결된 서버에서 실제로 접수한 제보자에 한정한다. 접수 때 봇이 발급하고 로컬에 보관하는 서명된 접수 증명으로 설치본과 수신자 범위를 확인한다. 봇이 정해진 수정 완료 서식과 발송 제한을 적용한다.
- 알림마다 고정된 발송 키를 사용하고, 같은 작업이 동시에 처리되지 않도록 로컬 큐와 DB에서 가드를 둔다. 발송 응답이 유실되는 짧은 구간에는 Discord의 메시지 `nonce`와 `enforce_nonce`를 사용하고, 결과를 확인할 수 없는 작업은 운영 화면에서 별도로 확인할 수 있게 한다. 처리 결과와 Discord 메시지 ID를 로컬에 남긴다. [Discord 메시지 생성 API](https://docs.discord.com/developers/resources/message#create-message)
- 재시도할 수 있는 연결 장애·요청 제한과 수신자 차단 등 확인이 필요한 발송 오류를 구분한다. 고객이 관리자 화면에서 대기·성공·실패 상태를 확인하게 한다.
- **완료 조건** — 대표 제보와 여러 중복 제보에 같은 사람이 섞여 있어도 각 고유 수신자에게 한 번씩 DM이 전송된다. 연결 재시작, 같은 작업 재처리, DM 차단과 발송 결과 유실을 각각 검증한다.

### 4단계 · 고객 배포 패키지와 최종 검증

- 고객이 받을 버전별 ZIP과 컨테이너 이미지를 만든다. `compose.yml`, 첫 실행 설정, 실행 상태 확인 방법을 포함한다. 실제 다운로드 주소, 봇 초대 경로, 검증한 OS·Docker 조건을 README에 넣는다.
- 종료·재시작·백업·복원·업데이트 방법을 문서화하고, 고객 장비에서 기존 데이터 볼륨을 사용해 각각 확인한다. 팀원이 내부 네트워크에서 웹을 함께 사용할 경우의 접속 범위와 인증 설정을 안내한다. 운영 봇의 배포 버전과 설치본 프로토콜 호환 범위도 기록한다.
- 루트 `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`와 테스트 전용 PostgreSQL 통합 테스트를 통과시킨다. 이전 로컬 점검에서 보였던 Google Fonts 다운로드와 Turbopack 빌드 오류는 실제 릴리스 이미지 빌드에서도 재현되는지 확인한다.
- **완료 조건** — 처음 보는 설치자가 README만 따라 새 장비에서 설치부터 실제 Discord DM 수신까지 성공한다. 설치·봇 버전, 발생한 문제, 백업·복원 결과를 남긴다.
