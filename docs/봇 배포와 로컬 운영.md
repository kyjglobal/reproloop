# 봇 배포와 로컬 운영

## 제공 봇 운영자

1. 기존 Discord 애플리케이션의 ID, 공개 키, 봇 토큰과 테스트 서버 ID를 준비합니다. Discord Developer Portal에서 서버 설치를 허용하고 `bot`과 `applications.commands`를 사용합니다. [Discord 앱 설치 문서](https://docs.discord.com/developers/quick-start/getting-started#installing-your-app)
2. `deploy/broker.env.example`을 `deploy/broker.env`로 복사해 운영 값과 32자 이상의 임의 `REPROLOOP_BROKER_SECRET`을 설정합니다. 이 비밀은 접수 증명 검증에 쓰이므로 실행마다 같은 값을 유지합니다. 봇 토큰과 접수 증명 서명 키는 봇 환경에 보관합니다.
3. Docker 호스트에서는 `docker compose -f deploy/compose.broker.yaml up --build -d --wait`를 실행하고 외부 HTTPS의 역방향 프록시를 로컬 `3100`으로 연결합니다. Railway에서는 저장소 루트의 Dockerfile, 같은 환경변수, `/data`에 연결된 영속 볼륨과 헬스체크 `/api/health`를 설정합니다. Railway 기본 볼륨의 쓰기 권한에는 `RAILWAY_RUN_UID=0`을 적용합니다. 봇은 로컬 설치본의 폴링 요청을 메모리에서 관리하므로 첫 배포에서는 인스턴스를 하나로 운영하고, 프록시 요청 시간 제한을 25초 이상으로 설정합니다. [Railway 볼륨 권한](https://docs.railway.com/volumes#permissions)
4. Discord Developer Portal의 Interactions Endpoint URL을 `https://<봇 주소>/api/discord/interactions`로 설정합니다. 기존 라이브 엔드포인트를 전환할 때는 준비된 이미지와 이전 배포로 돌아갈 방법을 먼저 확인합니다. [Discord 상호작용 수신·응답 문서](https://docs.discord.com/developers/interactions/receiving-and-responding)
5. 새 보조 테스트 서버에서 명령을 등록하고 고객 설치 절차를 검증합니다. 확인이 끝나면 `--global`로 서버 설치용 명령을 등록합니다.

   ```bash
   docker compose -f deploy/compose.broker.yaml exec broker pnpm --filter @reproloop/web discord:register-bug
   docker compose -f deploy/compose.broker.yaml exec broker pnpm --filter @reproloop/web discord:register-bug --global
   ```

6. 설치 파일을 전달할 때 `REPROLOOP_BROKER_URL`과 `REPROLOOP_DISCORD_APPLICATION_ID`가 채워진 고객용 설정 파일을 함께 제공합니다. 고객 설정에는 공개 접속 주소와 애플리케이션 ID가 들어갑니다.

## 고객 설치본 운영

- `docker compose --env-file customer.env ps`로 실행 상태를 확인합니다. 시작에 실패하면 `docker compose --env-file customer.env logs migrate web worker`를 실행합니다.
- `docker compose --env-file customer.env down`으로 종료하고 `docker compose --env-file customer.env up -d --wait`로 다시 실행합니다. 같은 폴더와 프로젝트 이름을 사용하면 기존 볼륨이 유지됩니다. [Compose 종료 동작](https://docs.docker.com/reference/cli/docker/compose/down/)
- DB와 웹은 기본 설정에서 설치 장비에 한정됩니다. 내부 팀원에게 웹을 제공하는 경우 조직의 접근 규칙에 맞는 HTTPS 주소를 `REPROLOOP_APP_URL`로 설정하고 웹 앞에 내부 프록시를 배치합니다.
- 업데이트 전에 PostgreSQL을 백업하고, 같은 폴더에 계약이 호환되는 새 설치 파일을 적용한 뒤 `docker compose --env-file customer.env up --build -d --wait`를 실행합니다. DB 마이그레이션은 컨테이너 시작 순서에 포함됩니다.

### PostgreSQL 백업과 복구 검증

아래 명령은 PostgreSQL의 데이터와 스키마를 파일로 내보내고, 같은 환경에서 별도 DB에 복원해 확인합니다. 고객 설치본에는 제보와 계정, 저장된 연결 자격 증명이 포함되어 있으므로 덤프 파일에 접근할 수 있는 사람을 제한합니다. 복구 후 같은 Discord 서버에서 새 연결 코드를 발급하면 설치본의 연결 자격 증명을 갱신할 수 있습니다.

```bash
docker compose --env-file customer.env exec -T db pg_dump -U reproloop -d reproloop -Fc -f /tmp/reproloop.dump
docker compose --env-file customer.env cp db:/tmp/reproloop.dump ./reproloop.dump
docker compose --env-file customer.env exec -T db createdb -U reproloop reproloop_restore
docker compose --env-file customer.env cp ./reproloop.dump db:/tmp/reproloop-restore.dump
docker compose --env-file customer.env exec -T db pg_restore --exit-on-error -U reproloop -d reproloop_restore /tmp/reproloop-restore.dump
```

운영 데이터를 받아 새 설치본을 구성하려면 새 폴더의 설치본에서 먼저 DB 서비스만 시작합니다. 아래의 `reproloop-recovery`는 복구 작업에 사용할 별도 Compose 프로젝트 이름입니다. 명령은 새 폴더에서 실행합니다.

```bash
docker compose --env-file customer.env -p reproloop-recovery up -d --wait db
docker compose --env-file customer.env -p reproloop-recovery cp ./reproloop.dump db:/tmp/reproloop-restore.dump
docker compose --env-file customer.env -p reproloop-recovery exec -T db pg_restore --exit-on-error -U reproloop -d reproloop /tmp/reproloop-restore.dump
```

복원 결과를 확인한 뒤 기존 설치본을 종료하고, 새 설치본에서 웹과 Worker를 시작합니다.

```bash
docker compose --env-file customer.env -p reproloop-recovery up --build -d --wait
```

기존 로컬 관리자 계정으로 로그인해 프로젝트와 제보를 확인합니다. Discord 연결 상태가 대기 상태로 남으면 같은 서버에서 새 연결 코드를 받아 입력합니다.
