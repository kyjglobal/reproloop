# 용준이에게 — Shared·Domain 이거 읽고 바로 쓰면 됨

결론부터 말하면 `packages/shared`랑 `packages/domain` 구현 끝남. 테스트도 38개 통과했고 빌드까지 확인했음.

이제 용준이가 할 일은 API마다 상태값이랑 권한 규칙을 새로 만드는 게 아님. 이미 만든 걸 가져다 쓰면 됨. 같은 규칙을 두 번 만들면 누가 손해 보냐? 결국 나중에 디버깅하는 우리 둘이 존나 손해 봄 ㅋㅋ

그리고 이것도 모르니? 정말 실망이다.

농담이고, 아래에서 필요한 부분만 찾아 쓰면 됨.

## 1. 핵심부터: 셋이 뭐가 다른데?

```text
shared: 들어온 데이터 모양이 맞는지 검사함
domain: 지금 이 처리를 허용해도 되는지 판단함
db: 판단이 끝난 결과를 저장하고 조회함
```

`apps`는 실행되는 프로그램이고 `packages`는 앱들이 가져다 쓰는 공통 코드임.

| 구분 | 실제 역할 |
|---|---|
| `apps/web` | 요청 수신, API, 로그인, 대시보드 |
| `apps/worker` | 알림과 백그라운드 작업 처리 |
| `packages/shared` | enum, Zod 스키마, API·job 계약 |
| `packages/domain` | 상태 전이, 권한, 중복 병합 규칙 |
| `packages/db` | Drizzle schema, migration, 실제 저장 |

처리 순서는 이거임.

```text
Discord 또는 Web 요청
→ apps/web가 받음
→ shared가 입력 검사
→ domain이 권한·상태·중복 규칙 판단
→ db가 PostgreSQL에 저장
→ 필요한 작업은 apps/worker가 처리
```

Shared와 Domain을 왜 굳이 나누냐고? 형식이 맞는 것과 실행해도 되는 것은 다른 문제라서 그럼.

```text
{ action: "mark_fixed", fixedBuildId: "..." }
```

이 요청은 형식이 맞을 수 있음. 근데 현재 상태가 `new`거나 요청자가 `member`면 실행하면 안 됨.

형식 검사는 Shared, 실행 가능 여부는 Domain. 기준부터 나누는 게 맞지.

## 2. `packages/shared`: 공식 용어집이자 계약서

Shared는 그냥 “다 같이 같은 말 쓰자” 패키지임.

이게 없으면 Web은 `investigating`, Worker는 `in_progress`, DB는 `checking` 같은 식으로 각자 상태값을 만들 수 있음. 처음엔 별일 없어 보이는데 API 붙이는 순간 개판 남. 어디서부터 틀렸는지 찾다가 “이게 뭔 지랄이지?” 소리 바로 나옴.

누가 잘못했는지도 애매함. 애초에 공통 기준이 없었으니까.

그래서 Shared를 단일 원본으로 둔 거임.

### 공통 enum

구현된 값은 아래와 같음.

- 조직 역할: `owner`, `admin`, `member`
- 제보 상태: `new`, `needs_info`, `investigating`, `reproduced`, `fixed`, `duplicate`
- 심각도: `low`, `medium`, `high`, `critical`
- 상태 변경 action
- 상태 이력 event
- 알림 종류와 처리 상태
- 제품 event
- Worker job 이름
- API 오류 코드

심각도 기본값은 `medium`임.

TypeScript `enum`을 별도로 하나 더 만들지 않았음. Zod enum이 원본이고 TypeScript 타입은 `z.infer`로 뽑음.

원본을 두 개 만들면 둘 중 하나는 언젠가 안 맞게 됨. 굳이 미래의 우리한테 폭탄 넘길 이유가 있나. 지금 3분 아끼고 나중에 3시간 처박는 병신 같은 거래는 하지 말자는 거임.

### API 응답 계약

단건 성공:

```json
{ "data": {} }
```

목록 성공:

```json
{
  "data": [],
  "meta": { "nextCursor": null }
}
```

오류:

```json
{
  "error": {
    "code": "INVALID_STATUS_TRANSITION",
    "message": "현재 상태에서는 요청한 상태로 변경할 수 없습니다.",
    "requestId": "req_01J...",
    "fieldErrors": {
      "fixedBuildId": ["수정 빌드가 필요합니다."]
    }
  }
}
```

규칙도 같이 고정했음.

- 단건 데이터가 없으면 `data: null`이 아니라 `404 NOT_FOUND`
- 목록 결과가 없으면 `data: []`
- 마지막 페이지면 `meta.nextCursor: null`
- `fieldErrors`는 필요할 때만 포함
- 계약에 없는 필드는 strict object에서 거부

응답 형식이 API마다 다르면 프론트에서 예외 처리 비용을 다 떠안게 됨. 서버가 편하자고 클라이언트에 비용 넘기는 구조, 그건 아니지.

### 요청과 Worker 계약

다음 Zod 스키마를 구현했음.


### API에서 쓰는 방식

```ts
const parsed = ReportTransitionSchema.safeParse(await request.json());

if (!parsed.success) {
  // VALIDATION_ERROR 응답으로 변환
}

const transition = parsed.data;
```

외부 입력에 바로 `as ReportTransition` 박는 건 검증이 아님. TypeScript한테 “아가리하고 통과시켜”라고 한 것뿐임.

런타임 데이터가 잘못되면 책임은 `as`가 안 져 줌. Zod 통과 전에는 믿지 않는 게 맞음.

## 3. `packages/domain`: 서비스 규칙을 판단하는 곳

Domain은 ReproLoop의 판단 담당임.

Shared를 통과했다고 무조건 실행하면 되는 게 아님. 현재 상태, 사용자 역할, version, 프로젝트 관계까지 봐야 함.

예를 들어 `mark_fixed` 요청은 아래 조건을 모두 만족해야 함.

- 현재 상태가 `reproduced`
- 요청자가 `owner` 또는 `admin`
- `expectedVersion`이 현재 version과 일치
- 수정 빌드가 같은 프로젝트에 속함
- 삭제된 제보가 아님

하나라도 안 맞으면 Domain에서 거부함.

이 규칙을 API route마다 복붙하면 어떻게 되겠음? 한쪽만 수정되고 다른 쪽은 그대로 남음. 결국 같은 요청인데 endpoint에 따라 결과가 달라지는 개같은 서비스가 탄생함.

규칙은 Domain 한 곳에 두는 게 맞지.

### 상태 전이

| 현재 상태 | action | 다음 상태 |
|---|---|---|
| `new` | `request_information` | `needs_info` |
| `new` | `start_investigation` | `investigating` |
| `new` | `mark_reproduced` | `reproduced` |
| `needs_info` | `start_investigation` | `investigating` |
| `investigating` | `request_information` | `needs_info` |
| `investigating` | `mark_reproduced` | `reproduced` |
| `reproduced` | `mark_fixed` | `fixed` |
| 일반 제보 | `merge_duplicate` | `duplicate` |
| `duplicate` | `unmerge_duplicate` | 병합 직전 상태 |

`fixed`는 MVP 최종 상태임. 이후 전이는 없음.

### 역할별 권한

| action | owner | admin | member |
|---|:---:|:---:|:---:|
| 정보 요청 | O | O | O |
| 조사 시작 | O | O | O |
| 재현 완료 | O | O | O |
| 중복 병합 | O | O | X |
| 병합 취소 | O | O | X |
| 수정 완료 | O | O | X |

`member`도 조회와 기본 처리는 가능함. 근데 병합과 수정 완료처럼 영향 큰 작업은 `owner/admin`만 가능함.

권한은 넓게 주고 사고 나면 막는 게 아니라, 필요한 만큼만 주는 게 기준임.

### 중복 병합 규칙

아래 요청은 전부 거부함.

- 자기 자신을 대표 제보로 지정
- 다른 프로젝트 제보와 병합
- 이미 `duplicate`인 제보를 대표로 지정
- 순환 참조가 생기는 병합
- 이미 병합된 대상을 다시 병합
- 오래된 `expectedVersion`으로 병합·취소
- 삭제된 제보를 조회·병합
- `member`가 병합·취소 실행

병합 취소 상태는 클라이언트가 마음대로 지정하지 않음. 저장된 병합 직전 상태를 서버가 복원함.

클라이언트한테 복원 상태를 맡기면 조작된 요청도 받아야 함. 서버가 이미 알고 있는 값을 왜 다시 믿어야 함?

### 알림 대상

대표 제보와 중복 제보의 Discord 사용자 ID를 합치고 아래 값을 제거함.

- 중복 ID
- 빈 문자열
- `null`, `undefined`

같은 사람한테 알림 세 번 보내고 “정상 처리입니다” 하면 사용자 입장에서는 뭔 개소린가 싶음 ㅋㅋ 중복 제거는 기본임.

### 주요 import

```ts
import {
  ReportDomainError,
  ALLOWED_REPORT_TRANSITIONS,
  getAllowedReportTransitionActions,
  canRolePerformReportAction,
  validateReportTransition,
  validateDuplicateMerge,
  validateDuplicateUnmerge,
  collectNotificationRecipientIds,
} from "@reproloop/domain";
```

타입:

```ts
import type {
  ReportRepository,
  ReportTransaction,
  ReportSnapshot,
  ReportTransitionInput,
  ReportTransitionDecision,
  DuplicateMergeInput,
  DuplicateUnmergeInput,
} from "@reproloop/domain";
```

### 상태 변경 API 예시

```ts
const transition = ReportTransitionSchema.parse(await request.json());

const decision = validateReportTransition({
  report,
  actorRole: membership.role,
  transition,
  fixedBuildProjectId: fixedBuild?.projectId,
});

// decision을 기준으로 DB transaction 실행
```

Domain 오류의 `code`는 공통 API 오류 코드와 맞춰 놨음. API route에서는 `ApiErrorSchema` 형태로 바꾸면 됨.

## 4. Domain에 DB 코드를 넣으면 안 되는 이유

Domain은 Next.js, Auth.js, Discord SDK, Drizzle을 직접 import하지 않음.

왜 이렇게 해 놨냐고? Domain이 프레임워크에 묶이면 규칙 하나 테스트하려고 DB와 서버를 전부 띄워야 하니까.

시간과 실행 비용은 누가 냄? 결국 개발자가 냄.

그래서 필요한 기능만 interface로 정의했음.

```text
domain: 어떤 조회·저장 기능이 필요한지 interface로 선언
db: Drizzle로 interface를 실제 구현
apps/web: 인증 정보와 repository를 domain에 전달
```

공개 interface:

```text
ReportRepository
ReportTransaction
```

Domain 파일에서 `NextRequest`나 Drizzle table import가 보이면 경계가 무너진 거임. 그 코드는 API나 DB로 보내면 됨.

## 6. 이건 먼저 해결해야 함: DB 상태 enum 불일치

여기가 제일 중요함.

현재 DB 상태값과 승인된 Shared·Domain 상태값이 다름.

현재 `packages/db/src/schema.ts`:

```text
new
triaged
in_progress
fixed
closed
duplicate
```

승인된 Shared·Domain 계약:

```text
new
needs_info
investigating
reproduced
fixed
duplicate
```

이 상태로 API를 연결하면 Shared에서 허용한 값이 DB에서 거부될 수 있음. 반대로 DB에는 있는데 Domain은 모르는 값도 생김. 그대로 밀면 진짜 좆됨.

누가 맞는지 애매한 문제가 아님. 둘이 다른 것 자체가 문제임.

권장 변경:

```text
triaged      제거 또는 needs_info로 교체
in_progress  제거 또는 investigating로 교체
reproduced   추가
closed       MVP에서 제거
```

기존 migration이 실제 DB에 적용됐는지가 기준임.

- 아직 적용 전: 초기 schema와 migration을 다시 맞출 수 있음
- 이미 적용 후: 기존 파일 덮어쓰기 금지, 새 migration 생성

둘이 동시에 migration 만들면 개같이 충돌하고, 그 비용은 누가 냄? 또 우리 둘이 냄 ㅋㅋ

한 명이 만들고 다른 한 명이 리뷰하면 됨. 기준부터 맞추자.

## 7. 용준이 담당 기능에서 이렇게 쓰면 됨

### Auth.js·권한

- 세션의 조직 역할을 `OrganizationRoleSchema`로 검증
- 상태 변경 전에 `validateReportTransition` 호출
- 간단한 UI 표시 여부는 `canRolePerformReportAction` 사용

### 제보 목록 API

- URL query는 `ReportListQuerySchema`로 검증
- 응답은 `createApiListResponseSchema` 계약 사용
- 결과가 없으면 `null` 대신 `[]`

### 상태 변경·수정 완료 API

```text
ReportTransitionSchema로 body 검사
→ validateReportTransition으로 상태·권한·version 검사
→ decision 기준으로 DB transaction 실행
```

상태 변경, 이력, 알림, job 생성은 한 transaction으로 처리해야 함. 앞의 셋은 저장됐는데 job만 실패하면 운영에서 원인 찾기 존나 귀찮아짐. 책임 소재까지 복잡해지고 누구도 행복하지 않음.

### Worker

- job payload는 `NotificationSendJobV1Schema`로 검증
- 알림 대상은 `collectNotificationRecipientIds`로 중복 제거
- 이미 전송된 알림인지 확인한 뒤 Discord 호출

## 8. 같이 지킬 규칙

1. API route에 상태 전이 조건을 다시 작성하지 않기
2. enum 문자열을 직접 만들지 말고 Shared에서 import하기
3. 외부 입력은 Zod 검증 전에 강제 형변환하지 않기
4. 계약 변경은 Shared부터 수정하고 리뷰받기
5. migration은 한 시점에 한 명만 생성하기
6. 상태·이력·알림·job 생성은 한 transaction으로 처리하기

“이번 한 번만 route에 직접 넣자” 할 수는 있음. 근데 그 책임도 미래의 우리가 짐.

잘되면 빨리 만든 사람 공이고, 망하면 유지보수하는 사람 탓? 그런 구조 만들 필요 없잖아.

공통 규칙은 공통 package에 두면 됨. 결국 그 얘기임.
